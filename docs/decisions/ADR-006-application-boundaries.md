# ADR-006：破坏兼容的应用边界与显式领域端口

## 状态

采用此方向，按完整用例实施。维护者要求重新设计抽象、架构和接口，且明确不需要后向兼容。本 ADR 不代表目标接口已经全部实现。

## 背景

现有 `App`/`AppState` 混合持久配置、来源发现、Shell I/O 和原生窗口工作。插件服务袋和通用字节 IPC 没有约束订阅与操作的不同语义；部分公开能力只有占位实现。继续扩展微内核或只按文件拆分，都不能修复这些所有权问题。

## 决策

1. 采用 Domain、Application、Presentation、Adapters、Native host 五个逻辑边界；首先在现有 crate 中建立真实用例，不立即拆出大量新 crate。
2. 分开持久 `WorkspaceDocument`、来源 `ObservationStore`、交互 `SessionState` 和只读 `ViewSnapshot`；来源健康和修订不等于配置修订。
3. 用例只根据类型化真实结果确认副作用。目录 Complete/Partial/Unavailable 不可混同；保存 Accepted/Committed 不可混同；取消不等于远端回滚。
4. 第一方扩展静态注册、显式注入类型化领域端口。组件契约与宿主内部任务生命周期分离；删除通用 service locator/DAG、字节 IPC、共享 token 和无效服务。
5. 保留 activation 回滚、owner 代际、close-before-cleanup、限时 drain 的性质，但不把内核对象暴露给 provider。组件与帧留在 UI 线程，worker 只传 owned Send 数据。
6. 新配置、Settings 与插件接口无兼容适配/自动迁移链。格式不支持或读取失败时保留用户原件，不当作第一次运行，不自动保存默认值。
7. 第一条实现链路为异步门户读取。随后替换文档保存、Settings、SPM 操作关联与帧/原生恢复。每条用例替换后删除对应旧入口，不维护两套 API。

具体接口、故障政策与验收矩阵见 [统一架构规范](../ARCHITECTURE.md)；阶段状态见 [路线图](../ROADMAP.md)。规范中的类型名是设计形状，实施时以实际使用的类型收敛，不添加未使用抽象。

## 比较过的替代方案

| 方案 | 结论 |
| --- | --- |
| 按当前 `App` 拆更多 impl 文件 | 只改善导航，不改变状态/错误所有权 |
| 扩大通用微内核和消息总线 | 将领域依赖藏到运行时；没有真实消费者证明收益 |
| 立即拆多个架构 crate | 容易固化尚未验证的 trait，增加跨 crate 迁移成本 |
| 模块化单体 + 显式端口 + 逐条真实用例 | 采用；依赖可见、失败可测试，必要时再提取 crate |
| 完整一次性重写原生渲染与 Shell | 不采用；无法通过单批变更证明 Windows 工作流正确 |

## 影响

- 旧配置/SDK/Settings 消息不再作为产品约束；旧用户文件不会被迁移或删除。
- 加入领域集成需要定义实际端口并在组合根接线，而不是注册字符串服务。
- worker、保存、Shell 和 SPM 结果必须带归属/修订与明确终态，相关故障测试属于交付本身。
- SPM wire 如果缺少关联/取消支持，需修改其独立仓库并验证配对，不在 UI 伪造保证。
- 旧 Cordis/P0–P2a 设计保留为历史资料，冲突时以本 ADR 和统一规范为准。ADR-005 的失效规则继续适用。

## 重开条件

有第二个真实宿主需要相同应用层时，评估提取 application/persistence crate；有真实动态插件或隔离需求时，另行设计 ABI/进程边界；测得有界 worker 被慢来源长期阻塞时，增加有界并行或辅助进程。不能以“未来可能扩展”为理由恢复通用服务框架。
